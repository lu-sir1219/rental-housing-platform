# 租房智能平台 — 消息通知系统设计框架

> 版本: 2026.1  
> 基于: 《预订流程、支付说明、消息通知与合同管理（优化版）》  
> 模式: 无自接版（超级管理员统一复核）

---

## 一、系统边界与职责

```
┌─────────────────────────────────────────────────────────┐
│                      租房智能平台                         │
│                                                         │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌─────────┐ │
│  │ 预订流程  │  │ 支付模块  │  │ 合同管理  │  │ 通知系统 │ │
│  │ (6步)    │  │ (3态)    │  │ (版本化)  │  │ (3通道)  │ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬────┘ │
│       │              │              │              │      │
│       └──────────────┴──────────────┴──────────────┘      │
│                          │                                │
│                    业务事件总线                            │
│               (同步触发 + 异步调度)                         │
└─────────────────────────────────────────────────────────┘
```

**通知系统的核心职责：** 将业务动作转化为多通道用户触达，保证可追溯、可重试、可审计。

## 二、业务事件矩阵

### 2.1 预订全流程（6 步）

| 步骤 | 事件 | 触发方 | 通知对象 | 时限要求 |
|------|------|--------|---------|---------|
| 1. 创建预订 | `booking_created` | 租客 | 租客（确认回执） | 即时 |
| 2. 支付押金 | `payment_created` | 系统 | 租客 | 即时 + 24h/12h/3h/1h 倒计时 |
| 3. 房源确认 | `property_confirmed` | 管理员 | 租客 | 3 自然日内 |
| 4. 发送合同 | `contract_generated` | 管理员 | 租客 | 即时 + 7 天/12h 倒计时 |
| 5. 签署合同 | `contract_signed` | 租客 | 租客 + 管理员 | 即时 |
| 6. 预订成功 | `booking_succeeded` | 管理员 | 租客 + BM + 房东 | 支付成功后 3 日内 |

### 2.2 用户触达矩阵（9 类事件 × 3 通道）

| # | 事件 | 站内 | 邮件 | 短信 | 触发时机 |
|---|------|:--:|:--:|:--:|----------|
| 1 | 支付创建 | ● | ● | ● | 支付订单生成后立即 |
| 2 | 支付失败 | ● | ● | ● | 支付网关返回失败 |
| 3 | 支付成功 | ● | ● | ○ | 支付确认后 |
| 4 | 支付过期 | ● | ● | ● | 超时自动取消 |
| 5 | 合同生成 | ● | ● | ● | 合同发送后立即 |
| 6 | 合同签署 | ● | ● | ○ | 签署完成后 |
| 7 | 预订成功 | ● | ● | ● | 全流程确认 |
| 8 | 预订取消 | ● | ● | ● | 取消/退款 |
| 9 | 退款完成 | ● | ● | ● | 退款到账后 |

> ● = 必须送达  ○ = 可选  — = 不发送

### 2.3 管理员通知

| 事件 | 触发条件 | 通道 |
|------|---------|------|
| 新合同待复核 | 租客签署完成后 | 站内 |
| 3 日未复核提醒 | 合同签署后超过 3 天未处理 | 站内（每日摘要） |
| 房东预订通知投递失败 | 房东邮箱未验证 | 站内（转人工） |

## 三、通道架构

### 3.1 三通道模型

```
                    ┌─────────────┐
                    │  业务事件    │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌─────────┐ ┌─────────┐ ┌─────────┐
        │ 站内通知 │ │  邮件   │ │  短信   │
        │ (实时)   │ │ (模板)  │ │ (模板)  │
        └────┬────┘ └────┬────┘ └────┬────┘
             │            │            │
        ┌────▼────┐  ┌───▼────┐  ┌───▼────┐
        │ DB 直写  │  │ Outbox │  │ Outbox │
        │ (同步)   │  │ →MQ/→  │  │ →MQ/→  │
        └─────────┘  └────────┘  └────────┘
```

### 3.2 各通道特性

| 特性 | 站内通知 | 邮件 | 短信 |
|------|---------|------|------|
| 存储模型 | `Notification` 表直写 | `NotificationOutbox` 发件箱 | `NotificationOutbox` 发件箱 |
| 发送模式 | 同步（事务内） | 异步（Celery 消费） | 异步（Celery 消费） |
| 模板引擎 | — | Jinja2 + `base.html` | 阿里云 SMS 模板变量 |
| 去重机制 | — | `event_key` 幂等 | `event_key` 幂等 |
| 重试策略 | — | 指数退避 (1m→5m→15m→1h) | 指数退避 |
| 失败处理 | — | 转人工 + 死信队列 | 转人工 |
| 提供商 | — | 阿里云 DirectMail → SMTP fallback | 阿里云 dysmsapi |
| 本地测试 | — | Mock SMTP Server | 控制台沙箱 |

### 3.3 降级路径

```
DirectMail ──失败──▶ SMTP ──失败──▶ 记录失败 + 告警
                         │
                    (配置为空时跳过)
```

## 六、调度策略

### 6.1 即时通知

- **触发：** 业务方法内联调用 `OrderNotificationService.enqueue()`
- **模式：** 事务内写入 Notification + Outbox，事务提交后 Celery 异步消费
- **去重：** `event_key` 唯一约束保证同事件不重复入队

### 6.2 定时提醒（Celery Beat）

| 任务 | 频率 | 扫描条件 |
|------|------|---------|
| `payment-reminder-3h` | 每 15 分钟 | `status IN (payment_pending, payment_processing) AND payment_expires_at < now + 3h` |
| `contract-unsigned-12h` | 每 30 分钟 | `contract.status = generated AND generated_at BETWEEN (now-7d, now-7d+12h)` |
| `admin-3day-review` | 每日 09:07 | `booking.updated_at > 3 days ago AND contract pending review` |

### 6.3 重试策略

- **邮件/短信：** 指数退避（1→5→15→60 分钟），最多 3 次
- **失败后：** `status = failed`，`last_error` 记录原因，站内通知管理员
- **人工兜底：** `/admin/outbox` 接口可查看失败队列并手动重试

## 八、扩展点

1. **微信模板消息：** `_CHANNEL_META` 已预留 `wechat_template` 字段，接入微信 SDK 后即可激活
2. **Push 通知：** 各通道在 `_dispatch_channels()` 中统一编排，新增通道只需实现对应的 Celery task
3. **多语言模板：** `template_version` 字段支持模板版本化，同一事件可有多语言变体
4. **用户偏好：** 可扩展 `user.notification_preferences` JSON 字段，让用户选择接收通道和频率
5. **房东自接版：** 当前架构预留 `LANDLORD_BOOKING_CONFIRMED` 事件，切换版本时只需激活对应分支
